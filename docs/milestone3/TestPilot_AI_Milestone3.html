1. Working Prototype

The prototype implements the Milestone 2 architecture as seven containers started by one command. It covers the complete M1 minimum demonstrable path — create project → enter requirements → generate candidate tests → review/edit and approve → execute approved tests → real runner outcomes and logs → quality/risk summary — plus a fourth use case.

1.2 Architectural structure

Style: layered Core Backend + event-driven test execution (ADR-001). Separate deployable units exist only where an ASR demands one: the Runner Worker and Test Sandbox for isolation (ASR-1), the AI Assistance Service for outage tolerance, privacy and replaceability (ASR-2, ASR-5), RabbitMQ for concurrent execution (ASR-4); the Execution Orchestrator stays inside the Core Backend so that one component owns all execution state (ASR-3).

2.2 QAS-3 Security — isolation of untrusted test code (ASR-1) — MET

Method. 15 test files submitted through the normal workflow (create → approve → run), one sandboxed run each. Every attack is written so that the test passes only if the attack succeeds — a PASSED attack would be a breach. A benign control test must pass (proves code really runs); a helper plants a marker that a test in a different project then searches for.

AttackOutcomeStopped by
read /etc/shadowFAILED (blocked)non-root user (uid 10001)
reach the Docker socketFAILEDsocket not present
internet / PostgreSQL / RabbitMQFAILEDnetwork_mode=none (unreachable, no name resolution)
run as root · read secrets from environmentFAILEDnon-root; no secrets passed to the sandbox
write outside /workFAILEDread-only root file system
fork bomb (500 processes) · memory bomb (2 GB)INTERRUPTED / RESOURCE_LIMITpids_limit, 256 MB limit without swap
fake pass with os._exit(0)INTERRUPTED / INVALID_REPORTorchestrator report validation (ADR-013)
read data left by another run / projectFAILEDcontainer + volume removed after every run
infinite loopINTERRUPTED / TIMEOUT after 32.9 skill from outside by the Runner Worker (T13)

Interpretation. The isolation is a property of the container boundary (T7, T8, T11, T13), not of the test code, so it holds for any user or AI-generated test. The fake-pass case shows ASR-1 and ASR-3 reinforcing each other. Limit: a documented suite on one machine; kernel-level container escapes are out of scope, as QAS-3 itself states.

2.3 QAS-7 Reliability — execution and evidence integrity (ASR-3) — MET

Method. (A) 40 run requests for DRAFT, REJECTED, edited-after-approval and mixed approved+draft tests. (B) 10 times: start a 20 s test, wait until RUNNING, docker kill both Runner Workers, wait for the final status, restart the workers so the redelivered job's late result also arrives. (C) a test that exits the interpreter before pytest writes its report.

PartTargetMeasured
A approval gate100 % rejected, no execution created40/40 409 TEST_NOT_APPROVED; 0 executions created
B runner crash100 % non-passing terminal state, traceable10/10 INTERRUPTED / RUNNER_LOST with execution ID and runner log; detected after 13.5 s (min) · 16.8 s (median) · 19.8 s (max); late results ignored
C invalid outputnever PASSEDINTERRUPTED / INVALID_REPORT

Interpretation. Approval check and execution insert share one database transaction; only the orchestrator writes status; the watchdog turns silence into INTERRUPTED; processed_message and immutable terminal states make redelivery harmless. Sensitivity point: detection time = 3 × 5 s heartbeat window + ≤ 5 s sweep; M1's earlier ≤ 10 s idea would need a 2 s heartbeat (more broker traffic) — a trade-off for the M4 ATAM.

2.4 QAS-2 Availability — AI-provider outage (ASR-2) — MET

Method. Baseline (AI generation → 201), then docker compose stop ai-service for 30 minutes. One client cycled through all unaffected core functions (read project, requirements, tests, executions, logs, coverage, risks; add a manual test); a second requested AI generation every 10 s and timed the answer. Then the AI service was restarted.

MeasureTargetMeasured
core requests succeeding during the outage≥ 99 %13,493 / 13,493 (100 %)
AI requests answered with an actionable errorall180 / 180 503 AI_UNAVAILABLE
time to the AI error≤ timeout (60 s) + 3 smax 0.08 s, p95 0.06 s
after recoveryAI works again201

Interpretation. The AI runs in its own container behind a timeout + circuit breaker (ADR-002, P9): its outage removes only AI features, and manual test entry keeps the workflow going. The breaker opened after 5 failures and answered without network calls. Limit: a stopped container fails fast; a provider that hangs until the timeout was not injected.

2.5 QAS-5 Scalability — 100 concurrent run requests (ASR-4) — MET

Method. One quick approved test; 100 POST /api/executions spread over 60 s by 10 clients; every execution polled until terminal. Queue wait = startedAt − createdAt. Tested capacity: 2 Runner Worker replicas.

MeasureTargetMeasured
unique execution IDs100 %100 / 100 (sent in 59.9 s)
terminal state100 %100 / 100 (all PASSED)
start within 30 s≥ 95 %100 % — p50 7.5 s, p95 12.8 s, max 13.2 s

Interpretation. Requests are accepted at once (202) and queued (P4); two competing workers take one job each (T16/T17). Each sandbox costs ≈ 1 s start-up, so 2 workers sustain ≈ 1.7 runs/s and the queue absorbed the burst at under half the target wait. Sensitivity point: number of replicas (--scale runner-worker=N) vs. isolation cost (ASR-1 ↔ ASR-4 trade-off, M1 §7.5).

2.6 QAS-1 Performance — result retrieval under load (not an ASR) — NOT MET

Method. Seeded inside the backend: one project with 1,000 test cases and 10,000 executions. 200 concurrent users for 15 minutes, each loading the latest results page and one execution, 0.5 s think time, 10 s client timeout. Unloaded, one request takes 14–16 ms (page 1 or page 500), so indexing and pagination (T15) work.

RunChangeRequestsErrorsp95p99ThroughputBackend after load
1as integrated11,77496.6 %1.44 s*1.54 s*13/shung
2session clean-up on the event loop——2.19 s2.35 s—hung
3+ admission control (ADR-018)69,2640.18 %1.37 s2.07 s77/shealthy

* run 1 latencies cover only the 3 % of requests that succeeded.

Interpretation. The experiment exposed a real defect: a convoy deadlock between FastAPI's 40 worker threads and the database pool — a live thread dump (run2-pyspy-thread-dump.txt) showed every thread waiting for a connection while every connection was held by a finished request waiting for a thread. ADR-018 fixed it (session clean-up on the event loop, explicit pool, 503 SERVICE_BUSY, admission control of 25 in-flight requests): errors fell from 96.6 % to 0.18 % and the backend stayed healthy. The latency target is still not met because of capacity, not query cost: one backend process served ≈ 77 req/s while 200 users with 0.5 s think time offer ≈ 140 req/s, so requests queue. QAS-1 is not an ASR (M1 §7.4) and can be met with standard techniques: more Core Backend processes or replicas, a short cache for the latest-results page, and a load generator on a separate machine. Trade-off: admission control favours availability (fast 503) over latency.

Example in full — ADR-018 (template of Appendix A)

ADR number & titleADR-018: Database session lifecycle, explicit pool sizing and admission control
StatusAccepted
Date & deciders27 November 2026 — Member 1 with Member 5 (found by the QAS-1 load test, Phase 5)
ContextUnder 200 concurrent users all 40 API worker threads waited for a database connection while every connection was held by a finished request waiting for a thread to serialise its response; cancelled requests also leaked connections. The backend stayed hung after the load stopped — an availability failure, not only a performance one.
Alternatives considered1. Bigger pool only — tried (run 2), the deadlock returned. 2. Fully async core (async SQLAlchemy) — removes the thread pool but is a large late change. 3. Async session dependency + explicit pool (20 + 10, 10 s timeout, 503 SERVICE_BUSY) + admission control (25 in flight, FIFO wait on the event loop, 503 after 5 s, health exempt) — chosen.
DecisionOption 3: app/core/database.py, app/api/errors.py, new app/api/admission.py; limits configurable in .env.
RationaleKeeping in-flight work below both the thread pool and the connection pool guarantees that a finishing request gets a thread and returns its connection; overload becomes fast, explicit 503s instead of a hang.
Consequences+ QAS-1 run 3: 69,264 requests, 0.18 % errors, health answering throughout, no stuck connections. + 10 regression tests. − Some requests get 503 under overload. − Latency target still not met (capacity); follow-up: more backend processes/replicas, short cache.

5.2 Integration test across component boundaries

tests/e2e/test_e2e_flow.py drives the composed system through the public API only and crosses every container boundary of Figure 1: Nginx → Core Backend → PostgreSQL; Core Backend → AI Assistance Service; Core Backend → RabbitMQ → Runner Worker → Docker sandbox → RabbitMQ → Core Backend. Steps: create project and requirement (UC-1); AI generation stored as DRAFT (UC-2); QA Assistant cannot approve (403); unapproved run rejected (409); approved AI test + failing test run in the sandbox → FAILED with per-test PASSED/FAILED and runner evidence (UC-3); AI explanation labelled as hypothesis; coverage and risks reflect the failure (UC-4). Result: 7 passed against docker compose up.
